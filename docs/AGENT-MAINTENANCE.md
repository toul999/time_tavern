# time_tavern 維護、打包與容器更新約定

本文件供後續 agent 使用。根目錄 `AGENTS.md` 為入口。以下記錄使用者已確認的操作方式；檔案結構、指令與限制以當前程式碼為準，若與本文不符，先查明差異並更新文件。

## 1. 開始工作：確認來源與範圍

1. 讀取適用的 AGENTS.md、Git 狀態與本次相關程式。保留使用者既有修改及資料。
2. 判斷工作是否僅改碼、僅建置映像、直接更新既有容器，或完整換版。使用者未要求部署時，完成改碼與驗證後回報即可。
3. 涉及正式部署時，查詢實際容器名稱、映像 ID、啟動指令、埠、執行帳號與 Mounts，確認使用者資料的真實位置。

完成條件：已辨識本次操作對象，以及「主機原始碼」「建置映像」「正式容器」各自的狀態，沒有靠舊對話猜測容器配置。

### Git 迭代約定

使用者已持續授權：自本約定起，每次實作程式功能或修正問題，完成相關檢查後建立本機 commit，保存該次完整迭代。無須每次重新詢問是否提交。不自動 push、改寫舊歷史或修改使用者 Git 身分。

README 的功能表每個日期一列，左欄只寫日期，右欄彙整當天功能。同一天即使有多個功能 commit，也合併到同一列；只在實際功能變更時新增或補充摘要。修改版不填 commit 編號，精確版本與提交次數由 Git 紀錄查閱；來源基準 commit 可保留。程式與對應摘要一起提交，不為回填 hash 額外建立 commit。

README、說明文件與 agent 指引的純文字或排版改動也照常提交，使用 `docs:` 類型訊息；這類 commit 不代表新增功能，不另外新增日期或功能紀錄。

1. 開始時查看工作目錄與暫存區，辨識既有未提交修改；不要順便提交先前累積或使用者自行修改的內容。若本次改動依賴既有未提交程式，先辨識依賴範圍，不能以不完整 commit 假稱可重建版本；必要時向使用者確認是否將既有修改納入基準。
2. 提交本次程式所需的原始碼、相依鎖定檔、相關測試與功能文件；用明確檔案或區塊選取，避免 `git add .`／`git add -A` 將其他內容混入。同一文件兼含程式與 Docker 修改時，僅暫存屬於程式的區塊。
3. 依使用者最新選擇，Dockerfile、.dockerignore、Compose、docs/DOCKER.md 與部署腳本均納入版本控制，確保 clone 後具有可用的建置配置。檔案只保留通用設定，不含個人 data、ENV、映像匯出檔或其他操作產物。
4. 僅建置、載入、匯出映像，或啟停、重啟、更新容器時，不建立 commit。若同時改動程式或部署設定檔，提交檔案變更，排除執行產物。
5. 檢查暫存差異與密鑰排除情況，執行相關驗證後提交有意義的訊息。沒有可提交的程式變更時，不建立空 commit。測試無法執行或有失敗時，先如實處理與說明，不能宣稱檢查通過。
6. 完成後確認 commit 範圍與 Git 狀態，回報短 hash、摘要及驗證結果。Git 寫入若遭權限或自動審查阻擋，保留修改並如實回報，不能假稱已提交。

此約定不代表將其他既有未提交修改自動補提交。程式與部署配置需維持可共同重建的版本；若新版缺少配置，依第 7 節重新建立。

提交前用 `git status` 查看檔案狀態、`git diff --cached` 檢查將提交的內容、`git check-ignore` 確認個人資料排除規則。`git status` 不是密鑰掃描器，`.gitignore` 也不會移除已追蹤或歷史 commit 中的秘密。另檢查追蹤檔案與暫存差異中的 Token／私鑰，僅回報檔名、行號及類型，不輸出秘密；有專用掃描工具時一併使用。未完成歷史掃描時不可宣稱整個倉庫歷史沒有機密。

## 2. 使用者已選擇的資料與重啟方式

- 目前預期不掛載 data；正式資料位於容器內。主機專案資料可能過時，不能拿來覆蓋正式資料。
- 新建映像只包含程式、依賴與 defaults，排除主機 data、個人 ENV 與備份。首次啟動初始化，最新資料由後續匯入承接。
- 一般重啟同一容器會保留其可寫層；移除或重建容器不會自動保留該層資料。`docker save` 保存映像，不保存運行中容器的最新資料。
- data 匯入成功後維持手動重啟。一般執行需關閉再開啟服務；容器可 restart 同一實例。重新整理網頁不足以還原。
- 一般執行、容器執行都須支援。使用者介面的說明使用「程式／服務」，不要假定所有人都使用 Docker。
- 現行 Compose 對外發布服務埠。保留使用者選擇；調整埠或只綁 localhost 時，需有對應需求。

參考實際配置：`Dockerfile`、`compose.yaml`、`.dockerignore`。供使用者閱讀的步驟在 [DOCKER.md](DOCKER.md)。

## 3. ENV：主設定與備份的優先順序

先查 `src/environment-backup.js` 與實際呼叫處。現行規則：

| 情況 | 行為 |
|---|---|
| 根目錄 `.env` 存在 | 以它同步更新 `data/environment.env` |
| 根目錄 `.env` 不存在、data 備份存在 | 從備份還原根目錄 `.env` |
| 兩份都不存在 | 不因同步函式就憑空生成；網頁儲存環境設定後才寫入 |
| 兩份都存在 | 根目錄優先，不比較修改時間；空白根目錄檔案也有優先權 |

網頁儲存環境設定、啟動及整份 data 匯出／匯入前會同步備份。外部編輯不會即時觸發同步；關閉程式沒有額外回存機制。

`environment.env` 只包含 `.env` 檔案內容；外部注入但沒寫入檔案的環境變數不包含在內。外部同名變數依目前 dotenv 設定優先；容器固定的 PORT 需保留與實際埠對應一致。

移植時以最新容器的 `.env` 與 data 為準。確認兩份存在且內容同步即可，避免顯示內容。不要把主機的空白或舊 `.env` 複製到新服務，否則它可能反過來覆蓋正確備份。

## 4. 修改功能時保留的行為

### 角色卡與整份資料備份

- 多張 PNG／JPG／JSON 匯入需序列儲存、保留整個選取清單、彙整壞檔原因；單張失敗不影響其他張，避免重複提交。
- 角色卡備份沿用 `cardstate.json` 結構，包含角色卡、助手卡與全局世界書。匯入先驗證，再備份原資料；保留 ID，不連帶匯入 ENV 或對話。
- 整份 data 備份會包含對話、圖片、密鑰等個人資料。區分「全局設定匯出」「角色卡備份」「data 備份」三種範圍，不要混用。
- data 還原整份取代，不合併。A 沒有、B 獨有的檔案也會移除；先讓使用者確認覆蓋。

### data 還原順序

沿用 `src/data-backup.js`：驗證 ZIP → 暫存 pending → 維護狀態 → 手動重啟 → 載入 ENV／狀態／Bot 前套用。

保留以下保護：

- 沒有 data 的首次使用也可處理。
- 路徑穿越、重複路徑、檔案與目錄衝突、容量與格式檢查；程式自產 ZIP 的完整性驗證。
- 先備份舊資料，並保留中斷還原的復原紀錄。
- 保留 data 根目錄本身，避免破壞掛載點。
- `.data-transfer` 是內部控制目錄，不納入匯出或映像，避免遞迴備份與意外執行舊 pending。
- 還原後同步處理根目錄 `.env`，避免舊設定覆蓋匯入資料；匯入沒有 environment.env 時，沿用程式的清空規則。

調整啟動流程時，同時檢查直接 `node src/index.js` 與 `npm start` 啟動器，確保兩者都在讀取設定前處理 pending。

## 5. 小修改：直接更新現有容器

適用於執行環境及依賴未變的程式更新。新增／刪除模組、資料格式變更或套件改動須先評估是否改走完整換版。

1. 在主機完成程式修改、相關測試及語法檢查，列出要新增、替換、移除的檔案。
2. 記錄目標容器與目前版本；停止生成並安排短暫停服。
3. 停止同一容器後，用 `docker cp` 將最新 data、根目錄 `.env` 與即將替換的程式備份到主機安全位置，檢查備份可讀且完整。
4. 將變更同步到該容器；同步處理新版已刪除的檔案，避免只覆蓋後殘留舊模組。`docker cp` 可以操作已停止容器。
5. 檢查路徑、擁有者及可讀寫權限。只更新指定程式檔，保留正式 data 與 ENV。
6. 啟動同一容器，檢查 HTTP、日誌與本次修改功能。失敗時回復先前程式；如啟動曾遷移資料，資料也須一起回復。

完成條件：驗證新功能與資料仍可使用，並告知「既有容器已修補，原始映像仍是舊版本」。後續重建前必須另外更新映像及處理最新資料。

## 6. 完整換版：重建映像與容器

1. 舊服務仍可運行時，先建置候選新版並驗證。使用獨立版本標籤，保留舊映像 ID，避免覆蓋唯一回退版本。
2. 候選映像不包含任何個人 data。程式及依賴有更新時重新建置，以最新容器備份在啟動後還原，避免程式版本與依賴不一致。
3. 切換前停止舊服務，從舊容器取得最終一致的完整 data 與 `.env`，核對檔案清單與大小。重要備份放在容器外，並排除 Git 與公開建置內容。
4. 保留已停止的舊容器。建立獨立命名的新版容器，將最終資料放入並檢查權限後再啟動。避免 Docker cp 的目錄語意造成 `/app/data/data`。
5. 資料放入前先清除新版預置 data 的內容，或透過受驗證的整份還原流程取代，避免舊初始資料與正式資料合併。以目標根目錄驗證約束清理範圍。
6. 驗證新服務後，才能清理舊容器與備份；實際刪除仍依使用者授權範圍執行。失敗時停止新版並恢復舊容器，避免兩個實例同時使用正式 Bot 憑證。

完成條件：新版來源版本、映像 ID、容器、備份位置及驗證結果均可追溯，正式資料與 ENV 已確認承接；回退路徑仍有效。

**資料 guardrail：** 無掛載情況下，`compose down`、`up --force-recreate` 或會重建現有服務的 `up --build`，只能在確認容器外最終備份與恢復方案後使用。不要把這些操作當成一般 restart。

## 7. 打包與測試

### Dockerfile 缺失、過時或取得新的原始碼時

使用者要求打包時，即使新版原始碼沒有 Dockerfile，也應依以下流程建立所需檔案；既有檔案只是起點，不作為程式結構的唯一依據。

1. **查執行方式。** 讀取當前 package.json、鎖定檔、啟動入口及其 import／檔案讀取路徑。確認是否新增編譯步驟、系統工具、原生模組或額外服務，並追蹤首次初始化與延後執行才會讀取的資源。
2. **列出建置及執行需求。** 使用下表核對。新版路徑不同時，以追查結果更新清單與 COPY 規則，不只複製固定幾個舊目錄。
3. **同步三份打包設定。** Dockerfile 決定建置及啟動，.dockerignore 決定可進入建置的檔案，Compose 決定執行與發布埠。三者必須一致，並維持使用者的「映像排除 data、後續匯入、無掛載」選擇。
4. **驗證真實映像。** 建置成功後，在獨立測試容器檢查必要檔案存在、排除項目不存在、沒有資料掛載、以非 root 正常啟動且能寫入資料。再測試首次初始化與資料還原。舊正式容器留在原處，直到部署分支的資料備份與切換條件完成。

完成條件：每項建置與執行需求都有映像中的對應來源，三份打包設定已同步，並有實際驗證或明確標示尚未能驗證的原因。

### 映像內容核對表

| 項目 | 現行專案如何處理 | 新版需再確認什麼 |
|---|---|---|
| Node.js 與系統環境 | 使用官方 Node 基礎映像 | 核對 engines、實際 API 需求、CPU 架構及原生依賴；不要無條件套用舊 Node 版本 |
| package.json 與 package-lock.json | 先複製，再以 npm ci 安裝正式依賴 | 鎖定檔存在且匹配；若套件管理器已變更，改用相符的鎖定安裝方式，而非硬套 npm ci |
| 全部後端模組 | 現為 src/，含備份、ENV 與重啟模組 | 檢查入口、動態 import、路徑外的共用模組，不只複製 index.js |
| 全部前端與靜態資源 | 現為 src/public/，含 vendor、圖片、字型、音效 | 若新版新增前端建置，納入建置階段及產物；建置依賴可能需 devDependencies，不能在編譯前就全部省略 |
| 初始化預設 | 現為 defaults/ | 確認程式首次啟動會讀哪些預設、模板或提示詞檔案，完整納入 |
| 必要腳本與其他資源 | 現行容器直接執行 src/index.js，不需 scripts/ 啟動器 | 新版若在運行或資料遷移時呼叫其他腳本、二進位工具、憑證或模板，要納入相應路徑，不能一律排除 scripts/ |
| 個人 data | 整個目錄排除，容器首次啟動建立 /app/data | 驗證初始化及後續匯入，不把主機的舊資料包入映像 |
| environment.env | 排除於映像，保留於遷移 ZIP | 確認正式服務的備份有同步最新 .env，匯入後可還原 |
| 根目錄 .env | 不進入映像，由 data 備份還原或網頁生成 | 確認新版仍有此還原機制；若機制改變，先設計相容遷移，再調整打包 |
| 授權文件 | 保留依賴自帶授權；另核對專案及資源的分發要求 | 必要 LICENSE／NOTICE 需加入允許清單及映像，不能因通用排除規則漏掉 |

### 排除項目與配置約束

- 一般排除主機 node_modules、.git、.runtime、本機日誌、測試、開發文件、agent 指引及無關的 Windows 右鍵工具。若其中某個路徑已成為新版的執行需求，按實際用途細分允許範圍。
- 排除 `data/.data-transfer/` 的 pending、復原紀錄、日誌及回退 ZIP；不要讓新容器啟動時誤套用舊還原工作。整個個人 data 都排除於映像，只透過匯入承接。
- 使用允許清單配合 COPY 時，新增檔案必須同時被允許且確實被複製。不要先把密鑰 COPY 進某一層，再於後續 RUN 刪除，以為映像已不包含它。
- 保留可寫程式目錄及 data 的帳號權限，因程式會生成根目錄 .env。若新版新增寫入位置，同步配置；不要改成整個根檔案系統唯讀後才發現設定無法保存。
- 啟動指令依新版實際入口設定，避免為了沿用 npm start 而再次觸發 Git 更新或互動式啟動器。確保訊號能傳到主服務；現行使用 exec 形式 CMD 與 Compose init。
- 同時檢查程式監聽位址、容器內埠、固定的 PORT、EXPOSE、健康檢查 URL 及 Compose 的主機埠對應。EXPOSE 本身不會開放主機埠。健康檢查要使用映像實際具備的工具。
- 不新增 VOLUME 指令、Compose volumes 或隱藏的匿名掛載來改變無掛載方案。若基礎映像本身宣告 VOLUME，也要檢查實際 Mounts。
- 不明確變更的執行參數先沿用使用者配置。容器內固定 PORT 是為避免跨裝置備份改埠，其他密鑰留給 ENV 資料流程，不硬寫到 Dockerfile 或 Compose。

### 程式修改的測試

- `.dockerignore` 採允許清單。若新增原始碼以外的必要資源，檢查它是否真的進入映像；本機 node_modules 由容器內 `npm ci` 取代。
- `defaults/` 是首次初始化所需，`src/public/` 的字型、圖片及 vendor 檔也需完整。
- 正式容器直接啟動 `src/index.js`，不走 Git 更新器。一般啟動器仍可保留 Git 更新行為。
- data 匯入手動重啟與環境設定中的重啟按鈕是不同功能；修改後者時避免重新引入前者的自動重啟。
- 修改前端時更新實際使用的資源版本參數，避免瀏覽器沿用舊檔。
- 新增依賴時一併更新 package-lock，重新建置；避免只把套件描述檔複製到舊依賴環境。

依變更選擇現有測試，讀取 package.json 取得指令。相關範圍：card-backup、data-backup、environment-backup、server-restart、startup-update、main-menu-navigation。執行 `node --check` 檢查修改的 JavaScript、`git diff --check` 檢查差異。

若沙箱使 Node 測試子程序 spawn EPERM，支援該旗標的 Node 可使用 `node --test --test-isolation=none` 跑指定測試；記錄採用的方式，不把啟動失敗當成測試通過。

需要容器驗證時，用獨立臨時容器及合成資料；禁止外部網路或明確停用 Bot 憑證，避免測試觸發真實訊息。確認 HTTP、無掛載、非 root 寫入、ENV 還原及手動 restart 還原；完成後清理自建臨時容器。

## 8. 部署前後的報告

交付須包含：修改內容與原因、測試及實際限制、是否影響資料格式、備份位置，以及是否已建置／啟動／更新正式服務。

特別標明：帶 data 的映像及 ZIP 可能含真實 API Key、Bot Token、圖片與對話，是私人產物。未獲授權不可推送到公開映像庫。刪除容器內檔案也不會抹除映像初始層中的內容。

長期記憶體診斷先區分容器用量、Node 程序與 WSL 整體占用，不用單張工作管理員截圖判定程式洩漏；設定記憶體上限前先確認 data 備份與可能的 OOM 影響。
